# Private Development Workflow

This repository is the private development counterpart to the public
`nikhgarg/EconCSLib` repository.

## Repository Layout

- `nikhgarg/EconCSLib`: public repository and public PR target.
- `nikhgarg/EconCSLib-private`: private development repository, with history
  based on public `main`.
- `nikhgarg/EconCSLib-private-archive-20260601`: archived copy of the old
  standalone private repository history.

Local remotes should use these names:

```bash
git remote add public https://github.com/nikhgarg/EconCSLib.git
git remote add archive https://github.com/nikhgarg/EconCSLib-private-archive-20260601.git
```

`origin` should point at `https://github.com/nikhgarg/EconCSLib-private.git`.
Disable pushes to the public remote from the private worktree so a private
`HEAD` cannot be published accidentally:

```bash
git remote set-url --push public DISABLED-PUBLIC-PUSH-FROM-PRIVATE
```

Public pushes belong only in the separate clean public-release workspace
described below.

## Sync Rule

Work on private `main` unless the user explicitly requests another branch.
Before starting private paper work, update private `main` without rewriting its
history, then refresh the fetch-only public reference:

```bash
git switch main
git pull --ff-only origin main
git fetch public
```

An explicit migration-wave freeze overrides repeated routine synchronization:
record the exact fetched private/public baselines and keep them fixed until the
wave is complete, a blocking dependency requires integration, or the user
reopens the boundary. Do not use remote commit count alone to justify another
pull or a full repository rebuild. For an integration inside the wave, inspect
changed-path and semantic/import overlap, run the focused affected checks, and
reserve the full build for demonstrated global impact or final release
readiness.

Do not rebase private `main` onto public `main`, force-push private `main`, or
push a private commit or branch to the public remote. Public export is a
content-selected operation from a fresh public base, not a private-history
merge.

## Shared Main Coordination

For every private-repository Git operation, follow
`skills/econcs-shared-worktree/SKILL.md`. It replaces routine stashes and
ad-hoc branches with tracked per-agent path leases and scoped checkpoint
commits:

```bash
python3 scripts/shared_worktree_status.py
python3 scripts/work_claim.py claim \
  --agent <stable-agent-name> \
  --scope papers/<PaperName> \
  --summary "<one-sentence task>"
python3 scripts/work_claim.py checkpoint \
  --agent <stable-agent-name> \
  --message "Checkpoint <paper or library seam>"
python3 scripts/work_claim.py release \
  --agent <stable-agent-name> \
  --message "Release <paper or library> lease"
```

Use `main` for disjoint leased scopes. Do not use `git stash`, `git add -A`, or
a task branch to park ordinary shared work. A branch or integration worktree is
an explicit exception for a user-requested branch or a clean, isolated merge;
record its purpose in the lease and remove it after the verified integration.
Before a handoff, run `python3 scripts/shared_worktree_status.py --strict` and
report every active lease, stash, dirty worktree, or unmerged branch rather
than hiding it.

## Public Release Workspace

Never create a public PR branch by pushing private `HEAD`. Create a separate,
clean clone whose `origin` is the public repository, and branch from the exact
fetched public base:

```bash
git clone https://github.com/nikhgarg/EconCSLib.git ../EconCSLib-public-release
cd ../EconCSLib-public-release
git fetch origin
git switch -c release/<ReleaseName> origin/main
```

Prepare a release-specific allowlist from
`scripts/public_release_allowlist.example.json`. Every entry must name one
exact file, a review reason, and `public_safety_reviewed: true`; directory
entries are rejected. Use `provenance: private_blob` plus the exact
private source commit for copied files, `public_base_deletion` for removals, and
`public_base_edit` for a reviewed in-place edit to a file already in the exact
public base. A `public_base_edit` entry pins SHA256 digests of both the public
base blob and candidate blob and cannot add, delete, rename, or change the Git
mode/type of the path. Use `public_base_addition` only for a reviewed public-only
file absent from both the public base and private source tree; it pins the exact
candidate blob SHA256 and cannot stand in for copied private provenance. Use
`public_generated` only for the four aggregate status/site files regenerated by
`scripts/sync_paper_status.py`. Keep paper entries scoped to:

- `papers/<PaperName>/`
- `papers/<PaperName>.lean`
- the paper's `status.json`
- any reusable library files required by the paper
- minimal docs or workflow updates needed for review

Apply only those reviewed paths to the clean public workspace. Do not copy the
private Git directory or merge/filter private history. Do not copy generated
aggregate status files; regenerate them in the public workspace after private
papers have been excluded.

Before committing, stage the candidate and verify that every repository-local
Lean import is present in the index and has no unstaged dependency:

```bash
python3 scripts/lean_import_closure.py --candidate index
```

Stage the complete reviewed export, regenerate the public aggregate surfaces,
and make one squashed release commit whose sole parent is the exact fetched
`origin/main` base. Multiple candidate commits and merge commits are rejected:
intermediate commits and deleted blobs would also be published by a push.

After the one candidate commit exists, run the candidate/PR check from the
canonical private checkout. It runs the complete remote, history, provenance,
visibility, source-leakage, generated-status, and Lean dependency checks
without reading or requiring human approval:

```bash
python3 /absolute/path/to/EconCSLib-private/scripts/public_release_candidate_guard.py \
  --repo "$PWD" \
  --allowlist /absolute/path/to/reviewed-public-export-allowlist.json
```

Resolve every candidate-check error before opening the PR. A successful check
prints the deterministic trusted-tooling bundle SHA256 and is sufficient for
another contributor to request review.

Only when a maintainer is ready to merge an accepted PR, the maintainer creates
the fixed approval artifact at
`~/.config/econcslib/public-release-approval.json`, using
`scripts/public_release_approval.example.json` as its schema. The artifact must
remain outside both repositories and pin the exact candidate commit, fetched
public base commit, allowlist SHA256, private guard SHA256, deterministic
private trusted-tooling bundle SHA256, and sorted set of private source commits.
The schema-2 tooling digest covers every non-test production file under the
executed private `scripts/` directory, including helpers imported or executed
by the guard; test files and interpreter caches are excluded. Pinning the
allowlist SHA256 also pins every
`public_base_edit` before/after blob digest in that allowlist. The guard has no
flag that can substitute another
approval path; do not ask an agent preparing the candidate to write this file.
Create the containing directory with mode `0700` and the approval file with
mode `0600`; the guard rejects symlinks and group/world-writable approval paths.

Leave the public worktree clean and have the maintainer run the merge guard from
the canonical private checkout,
passing the public clone through `--repo`. Do not execute the candidate's copy
of the guard. This command performs no fetch, push, or PR operation:

```bash
python3 /absolute/path/to/EconCSLib-private/scripts/public_release_candidate_guard.py \
  --repo "$PWD" \
  --allowlist /absolute/path/to/reviewed-public-export-allowlist.json \
  --authoritative
```

This merge-only command requires the fixed external schema-2
approval and checks all of its pins. The guard fixes its trust anchors to public `origin/main`, the `release/`
branch prefix, the private checkout containing the executed script, and that
checkout's `origin/main`. It requires canonical fetch and push URLs for both
repositories, separate Git common/object stores, one squashed commit directly
on the reviewer-approved public base, an approval-pinned exact-file allowlist
with no unused entries, private source commits reachable from private
`origin/main`, explicit public paper visibility, reproducible generated status
surfaces, and a dependency-closed Lean candidate. A candidate that passes the
ordinary candidate check may proceed to the public PR process; the approval pin
is only needed to merge it.

## Private Paper Checkpoint Commits

During active private formalization, checkpoint one paper at a time. A routine
private paper commit should include:

- `papers/<PaperName>/`
- `papers/<PaperName>.lean`, if it changed
- shared `AppliedModelingLib/`, script, or skill files explicitly needed by that paper

Do not refresh aggregate paper status, global site tables, or unrelated paper
audit sidecars merely to commit one private paper. Before staging, run the
paper-scoped checkpoint helper with every shared path that belongs in the same
commit:

```bash
python3 scripts/private_paper_checkpoint.py <PaperName> \
  --include-path AppliedModelingLib/Path/To/SharedFile.lean
```

The helper parses only the selected paper's JSON sidecars, directly elaborates
every tracked selected-paper Lean source and any explicitly included shared
Lean source, includes `papers/<PaperName>.lean` when present, checks whitespace
only on the selected paths, and prints an explicit
`git add -- ...` command. If a shared library batch affects multiple private
papers, make the library commit separately or include only the papers whose
builds you intentionally validated.

## Closeout Pacing And Follow-up Work

Freeze the selected paper's source, interface, and canonical evidence before
strict closeout. Run each unchanged expensive closeout lane once. After a
failure, repair only a verified current integrity problem—source/map or
closure mismatch, invalid receipt authority, proof failure, or a checker that
contradicts current authoritative evidence—then run its one planned successor.

Record any other audit, performance, renderer, report, or workflow improvement
as a concrete deferred task. Commit and validate it after the paper has an
accepted closeout receipt; do not replan or rerun the paper merely to test it.
Before attributing a stale receipt to an engine change, compare the old and new
plan `content_inputs`: compatible engine and workflow edits are not paper
evidence unless the comparison identifies a material lane input.

When both a paper closeout and such a deferred workflow improvement are ready,
make and push the paper-closeout commit first. Make the project-skill, planner,
audit, or ergonomics follow-up a separate commit afterward. Do not fold that
follow-up into the accepted paper evidence or rerun the paper just to exercise
the improvement.

Do not turn a cache invalidation, audit diagnostic, receipt-format edit, or
report-only correction into a closeout-time integrity repair without first
identifying the frozen content input and the accepting consumer it changes. If
the source/Spec/proof surface and receipt authority are unchanged, record the
work as deferred and preserve the accepted evidence lanes until the paper is
closed.

Run current-evidence and artifact preflights before the expensive primary Lean
gate when the strict transaction supports them; the complete strict audit
remains the acceptance check. If a restricted environment loses a detached
closeout worker, inspect its recorded state and run the exact plan-pinned
command in the foreground once rather than launching duplicate workers.

## Machine-Readable Status

Every paper folder, public or private, owns its status in
`papers/<PaperName>/status.json`. Every record must explicitly set
`repository_visibility` to `public` or `private_only`; publication venue
metadata never grants repository-export authority. For a private checkpoint commit, the
paper-local status is enough; do not regenerate the aggregate solely because
one unfinished private paper changed. Regenerate the aggregate only for a
release-oriented update, public sync, broad status pass, or explicit user
request:

```bash
python3 scripts/sync_paper_status.py
```

The aggregate `papers/status.json` is generated. README tables, dashboards, and
future site generation should read from the paper-local JSON files or the
generated aggregate rather than maintaining separate status logic.
